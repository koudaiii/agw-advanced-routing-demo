2. 前提条件

  • Azure サブスクリプションと、リソース グループを作成できる権限
  • Azure CLI (az login 済み)。ガイドのデプロイは、deploy.sh から Bicep で行う (Bicep は az に同梱)。Advanced routing の CLI コマンド (az network application-gateway advanced-routing-set / advanced-routing-map) は Azure CLI 2.92.0 以降で使える。5.1 では、これらで実機を確認する
  • bash 環境 (Azure Cloud Shell で可)。SSH 鍵 (~/.ssh/id_ed25519.pub) がなければ deploy.sh が自動作成
  • WAF_v2 の Application Gateway は稼働時間で課金されます。デモ後は後片付けを実施してください

3. バックエンドの作り方

3.1 設計方針

  • どのプールが応答したかが一目で分かる: プール名を大きく表示し、プールごとに色を変える。応答ヘッダー x-backend-pool にも入れて curl で判定できるようにする
  • ゲートウェイを通った証拠を見せる: 受信ヘッダーを全件表示し、App Gateway が付与する x-forwarded-for / x-forwarded-proto / x-forwarded-port / x-original-host などを強調
  • 1 ファイル・依存なし: Node.js 標準モジュールのみ。プールの違いは環境変数だけで表現
  • ヘルス プローブ用エンドポイント: /healthz が 200 を返す
  • 安全な表示: 受信値はすべて HTML エスケープして表示 (ヘッダー経由の注入を防ぐ)

3.2 エンドポイント

パス応答
/healthz200 ok (App Gateway のプローブ用)
任意のパスHTML: プール名・インスタンス・Method・Path・Query・受信ヘッダー一覧
任意のパス ?format=json または Accept: application/json同じ内容の JSON

3.5 VM への配置 (cloud-init + systemd)

deploy/make-cloud-init.sh が、VM ごとに 1 つずつ初期化ファイルを生成します (deploy.sh が実行します)。引数で入力 (プール定義) と出力ファイルを指定します。

  • cloud-init.yaml: VM 1 用。backend/pools.conf の 7 プロセス (ポート 8080–8083、8085、8086、8087)
  • cloud-init-canary.yaml: VM 2 用 (カナリア)。backend/pools-canary.conf の pool-canary (ポート 8080)、pool-fast (8086)、pool-rr-b (8087)

どちらも中身は次の 3 点です。

  1. NodeSource の apt リポジトリから Node.js 26 (現行の LTS) をインストールし、server.js を /opt/agw-demo/ に配置 (base64 埋め込み)。リポジトリの署名鍵は、起動時に取得せず、ファイルに埋め込んでいます (deploy/nodesource-repo.gpg.key)。Ubuntu 標準の nodejs パッケージ (Node.js 18、サポート終了) は入らないように固定しています。そのため、NodeSource に届かないときは、Node.js 18 に戻らずにインストールが失敗します
  2. テンプレート ユニット agw-pool@.service を作成 (DynamicUser=yes で専用ユーザーなしに実行)
  3. プールごとに /etc/agw-demo/<pool>.env を作り、systemctl enable --now agw-pool@<pool>
[Service]
EnvironmentFile=/etc/agw-demo/%i.env
ExecStart=/usr/bin/node /opt/agw-demo/server.js
Restart=always
DynamicUser=yes

バックエンド VM にはパブリック IP を付けません。外向き通信 (パッケージ取得など) は NAT Gateway 経由です。受信は NSG の既定ルールで遮断するため、インターネットからバックエンドへ直接は到達できず、App Gateway 経由のみになります。

手順は deploy/deploy.sh に集約しています。CLI で 1 つずつ作る必要はありません。deploy.sh が deploy/main.bicep のテンプレートをデプロイし、次のリソースをまとめて作成します。

優先度ベース (ポート 8090) の確認

8090 番は、VM 2 の pool-canary (Primary) を優先し、止まると VM 1 の pool-web (Standby) に切り替わります。canary-check.sh は応答ヘッダーの x-backend-pool (VM 上のプロセス名) を数えるため、Primary は pool-canary、Standby は pool-web と表示されます。

FRONTEND=<フロントエンド IP>:8090 ./canary-check.sh /app/home 100   # 正常時
# VM 2 の pool-canary を停止し、2〜3 分待つ
az vm run-command invoke -g rg-agw-advrouting-demo -n agwdemo-backend-canary --command-id RunShellScript --scripts "systemctl stop agw-pool@pool-canary"

期待結果 (例):

正常時   100 件すべて pool-canary (Primary = VM 2)
停止後   100 件すべて pool-web    (Standby = VM 1)
復旧後   100 件すべて pool-canary (Primary = VM 2)

停止後の切り替えには約 2〜3 分かかります。直後に確認すると、まだ pool-canary が返ることがあります。このプロセス (VM 2 の 8080 番) は、8080 番の pool-canary と 8100 番の pool-flag-on の唯一のサーバーでもあります。停止中は、ポート 8080 の約 10% と、ポート 8100 の X-Feature: new の要求も失敗します。確認が終わったらすぐ復帰してください。(重み付けはプールの正常性を見ないため、8080 番で pool-canary が選ばれた要求は失敗します。8 章を参照。)停止中は test.sh の 8080 番と 8100 番の結果が失敗することがあるため、test.sh は復帰後に実行してください。

機能フラグ (ポート 8100) の確認

8100 番では、クライアントがヘッダーでフラグをオンにします。flagMap は、ヘッダー X-Feature: new の要求を pool-flag-on (VM 2 の 8080 番) に送り、それ以外は既定の pool-flag-off (VM 1 の 8080 番) に送ります。x-backend-pool はプロセス名なので、オフは pool-web、オンは pool-canary と表示されます。

curl -s -D - -o /dev/null http://<フロントエンド IP>:8100/ | grep -i x-backend-pool
curl -s -D - -o /dev/null -H "X-Feature: other" http://<フロントエンド IP>:8100/ | grep -i x-backend-pool
curl -s -D - -o /dev/null -H "X-Feature: new" http://<フロントエンド IP>:8100/ | grep -i x-backend-pool
ヘッダーなし      x-backend-pool: pool-web     (pool-flag-off、オフ)
X-Feature: other  x-backend-pool: pool-web     (pool-flag-off、オフ)
X-Feature: new    x-backend-pool: pool-canary  (pool-flag-on、オン)

ポート 80 には機能フラグのルールがありません。必ず 8100 番を使います。クライアントが選ぶ方式で、ランダムには分けないため、A/B テストではありません (統計的な A/B テストは #27 で扱います)。

サーバー選択 (ポート 8110 / 8120 / 8130)

この 3 つのポートで、1 つのプールの中でゲートウェイがサーバーをどう選ぶか、1 台が詰まったとき (hot spot) に何が起きるかを見せます。8110 は速い 2 台の Round Robin です。8120 は pool-slow (3 秒待つ) と pool-fast の Round Robin で、約半分の要求が待たされます。8130 は同じ 2 台の Least Connections で、新しい要求は遅いサーバーを避けます。x-backend-pool には応答したサーバーが出ます。

FRONTEND=<フロントエンド IP>:8110 ./lb-check.sh /app/home 100 6
FRONTEND=<フロントエンド IP>:8120 ./lb-check.sh /app/home 100 6
FRONTEND=<フロントエンド IP>:8130 ./lb-check.sh /app/home 100 6
ポート振り分け (100 件、同時 6 件)全体の所要時間
8110pool-rr-a と pool-rr-b が約半分ずつ短い
8120pool-slow と pool-fast が約半分ずつ長い。約 25 秒以上
8130pool-slow が 10 件以下8120 より明らかに短い

Least Connections と Round Robin の差は、遅いサーバーに前の要求が残っている間にだけ出ます。そのため lb-check.sh とシミュレーターのテスト要求は、同時に 6 件を保って送ります (1 件ずつ送る canary-check.sh では差が出ません)。ポートは 1 つずつ試してください。8120 と 8130 は同じ 2 台を使います。3 秒の遅延はプローブのタイムアウト (20 秒) より短いため、遅いサーバーも正常のままです。応答しなくなったサーバーは、どちらのアルゴリズムでもプローブで外れます。Cookie によるアフィニティが有効だと Least Connections は使われないため、hs-8086 では無効にしています。

4.3 ポータルでヘッダーベースのルールを手動で作る (チュートリアルの手順)

Microsoft Learn の チュートリアル: Azure ポータルで Application Gateway の Advanced Rules を使ってヘッダーベースのルーティングを設定する の手順です。このデモは deploy.sh が作るため、通常は不要です。ポータルの操作を確かめるときに使います。

ポータルの「アプリケーション ゲートウェイの作成」では Advanced ルールを設定できません。基本ルールで作成した後に、基本ルールを Advanced に変更します。

前提: 基本ルール、リスナー、既定のバックエンド プールと設定がある Application Gateway。v2 用の 2 つ目のバックエンド プールと、そのバックエンド設定。

  1. ゲートウェイの ルール を開き、基本ルールを選ぶ。
  2. ルールの種類 を Advanced にする。
  3. リスナー タブ: ルール名 (例: rule1) と ルールの優先度 を入力する。数値が小さいほど先に評価される。リスナーは既存のものが事前に入る。
  4. ルーティング タブ: Advanced ルール名 (例: V2-app-routing) と Advanced ルールの優先度 を入力する。
  5. 条件: + Add conditions で条件セットを作る。
    • 条件セット名: V2-app-condition (条件セットの名前であり、ヘッダー名ではない)
    • 条件の種類: HTTP header / ヘッダーの種類: Custom / カスタム ヘッダー: X-App-Version / 一致の種類: Static / 値: v2
    Add Conditions を押しても、この時点ではまだ保存されない。
  6. ターゲット: + Add Targets。ターゲットの種類: Backend pool / バックエンド プール: v2 用のプール / バックエンド設定: v2 用の設定。
  7. 既定のターゲット: 基本ルールの Target と Backend Settings と同じ値になっていることを確認する (既定の振り分け先)。
  8. Review → Save。

テスト

curl http://<FRONTEND-IP>/                              # 既定のプール
curl -H "X-App-Version: v2" http://<FRONTEND-IP>/      # v2 のプール
curl -H "X-App-Version: none" http://<FRONTEND-IP>/    # 既定のプール

注意 (実際に起きた間違い)

  • 条件セット名をヘッダー名の欄に入れると、一致しない: ヘッダー名が V2-app-condition になると、X-App-Version: v2 は一致せず、既定の振り分け先に送られる。ヘッダー名は必ず X-App-Version。
  • 既存のルールを変えると、動きが変わる: partner を V2-app-routing に変えて X-App-Version: v2 の条件を AND で追加すると、X-Partner-Id だけのリクエストは pool-partner に届かなくなる。
  • ポータルでの手作業は、再デプロイで消える: deploy/main.bicep の定義で作ったルールは、deploy.sh を実行すると定義どおりに戻る。

5.2 シミュレーターから実機へ直接送信する (ブラウザーの制約)

単体 HTML 版 agw-routing-simulator.html は、画面上部の「ゲートウェイ URL」が空ならオフラインでシミュレーションし、URL を入れると実機に要求を送って「予測」と「実機の応答」を並べて表示します (予測と一致 / 不一致も表示)。ファイルをローカルで開けば (file://) http のゲートウェイにも送れます。ブラウザーの制約は次のとおりです。

課題原因対応
HTTPS (https のページから使う場合)https で配信されたページから http のゲートウェイへの fetch は混在コンテンツとしてブロックされる単体 HTML をローカル (file://) で開く。https のページから使う場合は HTTPS リスナーを追加
CORS別オリジンへの fetch でカスタム ヘッダー (X-Tenant-Id など) を送るとプリフライト (OPTIONS) が発生全プールの server.js で OPTIONS に応答し、Access-Control-Allow-Origin / -Allow-Headers / -Expose-Headers: x-backend-pool を返す。OPTIONS 自体も App Gateway のルーティングを通るため、全プールで同じ処理が必要
User-Agent を変えられないブラウザーの fetch では User-Agent を任意に設定できないモバイル ルールは、実機のスマートフォンで開くか、curl -A で見せる
Client IP は実際の IPブラウザーから送る要求の送信元は端末の実 IP実機モードの予測は、ゲートウェイが見ている送信元 IP を使う。WAF は、User-Agent (agw-block-demo) を遮断するルールと curl -A で見せる
リダイレクトを読めないfetch はリダイレクトを自動追従、redirect: "manual" では Location を読めない「リダイレクトされた」ことだけを表示する
WAF 403 の中身を読めないWAF の応答には CORS ヘッダーが付かず、fetch がネットワーク エラーになるエラー時は「ブロックされた可能性」として表示し、curl で 403 を確認

server.js には次の CORS 対応を組み込み済みです (環境変数 ALLOW_ORIGIN、既定は *。空文字で無効化)。

const ALLOW_ORIGIN = process.env.ALLOW_ORIGIN === undefined ? "*" : process.env.ALLOW_ORIGIN;
function cors(res) {
  if (!ALLOW_ORIGIN) return;
  res.setHeader("access-control-allow-origin", ALLOW_ORIGIN);
  res.setHeader("access-control-allow-methods", "GET, HEAD, POST, PUT, DELETE, PATCH, OPTIONS");
  res.setHeader("access-control-allow-headers", "*");
  res.setHeader("access-control-expose-headers", "x-backend-pool");
  res.setHeader("access-control-max-age", "0");
}
// createServer の先頭で:
cors(res);
if (req.method === "OPTIONS" && req.headers["access-control-request-method"]) { res.writeHead(204); return res.end(); }

5.3 テスト要求 (件数分をまとめて送る)

「テスト要求を送る」は、選んでいる要求をそのポートに件数分 (既定は 100 件) 送ります。同時に 6 件を保って送り、各要求に応答したプールまたはサーバー、プールごとの平均時間、全体の所要時間を「実機の応答」に表示します。1 件では分からないポート、つまりカナリア (8080)、優先度ベース (8090)、サーバー選択 (8110 / 8120 / 8130) の確認に使います。送る要求は、「要求を送信」と同じく入力欄の内容 (メソッド、パス、クエリ、ヘッダー) です。ただし User-Agent のように、ブラウザーがページから設定させないヘッダーは送りません。どちらのボタンを押しても、予測は入力欄の内容で出し直します。ポート 8080、8090、8110〜8130 はヘッダー、メソッド、パス、クエリでは振り分けないため、これらのポートでは予測にその旨を表示します。送信中にもう一度押すと、まだ送っていない要求を取り消します。10 秒以内に応答がない要求は、失敗として数えます。

8. 制約・注意事項

  • Advanced rules はプレビュー機能です。マルチサイト リスナーと L4 (TCP/TLS) プロキシでは使えません
  • 複数プール (重み付け・優先度ベース) は v2 SKU (Standard_v2 / WAF_v2) で使え、Basic ルール、Advanced ルール、Advanced routing map の既定アクションに設定できます。1 か所につき最大 5 プールで、方式はどちらか一方です。このデモは :8080 と :8090 の Advanced routing map に設定しています
  • 重み付けはプールの正常性を見ません。選ばれたプールに正常なサーバーがなければ、要求は失敗します。正常性で切り替えるなら、優先度ベースを使います
  • 上限: マップ 100 / ゲートウェイ、条件セット 10,000 / ゲートウェイ、ルール 100 / マップ、条件 5 / 条件セット、値 5 / 条件、値・正規表現 128 文字
  • WAF ポリシーはゲートウェイまたはリスナー単位で関連付け。ルール単位の WAF ポリシーは非対応
  • シミュレーターの判定はブラウザーの正規表現エンジンで近似しており、RE2 と完全には一致しません
