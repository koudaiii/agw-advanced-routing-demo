2. 前提条件

  • Azure サブスクリプションと、リソース グループを作成できる権限
  • Azure CLI (az login 済み)。高度なルールは CLI (2.87.0 時点) では作れないため、ガイドのデプロイは Bicep で行う (Bicep は az に同梱)
  • bash 環境 (Azure Cloud Shell で可)。SSH 鍵 (~/.ssh/id_ed25519.pub) がなければ deploy.sh が自動作成
  • WAF_v2 の Application Gateway は稼働時間で課金されます。デモ後は後片付けを実施してください

3. バックエンドの作り方

3.1 設計方針

  • どのプールが応答したかが一目で分かる: プール名を大きく表示し、プールごとに色を変える。応答ヘッダー x-backend-pool にも入れて curl で判定できるようにする
  • ゲートウェイを通った証拠を見せる: 受信ヘッダーを全件表示し、App Gateway が付与する x-forwarded-for / x-forwarded-proto / x-forwarded-port / x-original-host などを強調
  • 1 ファイル・依存なし: Node.js 標準モジュールのみ。プールの違いは環境変数だけで表現
  • ヘルス プローブ用エンドポイント: /healthz が 200 を返す
  • 安全な表示: 受信値はすべて HTML エスケープして表示 (ヘッダー経由の注入を防ぐ)

3.2 エンドポイント

パス応答
/healthz200 ok (App Gateway のプローブ用)
任意のパスHTML: プール名・インスタンス・Method・Path・Query・受信ヘッダー一覧
任意のパス ?format=json または Accept: application/json同じ内容の JSON

シミュレーターのプール一覧と同じ名前・色にそろえているため、シミュレーターの「応答」パネルと実機のページが同じ見た目になります。

pools.conf は、VM 上で動く Node.js プロセス (待ち受けるポート) の定義です。ポート 8090 は、Application Gateway のリスナーのポートで、バックエンドのプロセスは 8090 番を待ち受けません。優先度ベース (8090) は、次のゲートウェイのプールを使い、それぞれ既存のプロセス (8080 番) を指します。

ゲートウェイのプール指す先 (VM とプロセス)使われる場面
pool-primaryVM 2 (192.168.1.11) の pool-canary プロセス (:8080):8090 の優先度 1 (Primary)
pool-standbyVM 1 (192.168.1.10) の pool-web プロセス (:8080):8090 の優先度 2 (Standby)、既定
pool-webVM 1 の pool-web プロセス (:8080):80 の既定、:8080 のカナリア 90%
pool-canaryVM 2 の pool-canary プロセス (:8080):8080 のカナリア 10%、:80 の変種 B (X-Variant: B)

3.4 サーバー本体 (backend/server.js) の要点

backend/server.js の抜粋です (環境変数の読み取り、CORS、リクエストの処理)。

const POOL_LABEL = process.env.POOL_LABEL || POOL_NAME;
const POOL_COLOR = /^#[0-9a-fA-F]{6}$/.test(process.env.POOL_COLOR || "") ? process.env.POOL_COLOR : "#334155";

const ALLOW_ORIGIN = process.env.ALLOW_ORIGIN === undefined ? "*" : process.env.ALLOW_ORIGIN;

function cors(res) {
  if (!ALLOW_ORIGIN) return;
  res.setHeader("access-control-allow-origin", ALLOW_ORIGIN);
  res.setHeader("access-control-allow-methods", "GET, HEAD, POST, PUT, DELETE, PATCH, OPTIONS");
  res.setHeader("access-control-allow-headers", "*");
  res.setHeader("access-control-expose-headers", "x-backend-pool");
  res.setHeader("access-control-max-age", "0"); // preflight is routed too; do not cache it
}
// ... (中略: ヘッダー名の定義、page() の HTML 生成) ...
http
  .createServer((req, res) => {
    cors(res);
    if (req.method === "OPTIONS" && req.headers["access-control-request-method"]) {
      res.setHeader("x-backend-pool", POOL_NAME);
      res.writeHead(204);
      return res.end();

      res.writeHead(200, { "content-type": "text/plain" });

    }

    res.setHeader("x-backend-pool", POOL_NAME);
    res.setHeader("cache-control", "no-store");
    if (wantsJson) {
      res.writeHead(200, { "content-type": "application/json; charset=utf-8" });
      return res.end(JSON.stringify(s, null, 2));
    }
    res.writeHead(200, { "content-type": "text/html; charset=utf-8" });

3.5 VM への配置 (cloud-init + systemd)

deploy/make-cloud-init.sh が、VM ごとに 2 つの初期化ファイルを生成します (deploy.sh が実行します)。引数で入力 (プール定義) と出力ファイルを指定します。

  • cloud-init.yaml: VM 1 用。backend/pools.conf の 5 プール (ポート 8080–8083、8085)
  • cloud-init-canary.yaml: VM 2 用 (カナリア)。backend/pools-canary.conf の pool-canary (ポート 8080)

どちらも中身は次の 3 点です。

  1. Node.js をインストールし、server.js を /opt/agw-demo/ に配置 (base64 埋め込み)
  2. テンプレート ユニット agw-pool@.service を作成 (DynamicUser=yes で専用ユーザーなしに実行)
  3. プールごとに /etc/agw-demo/<pool>.env を作り、systemctl enable --now agw-pool@<pool>
[Service]
EnvironmentFile=/etc/agw-demo/%i.env
ExecStart=/usr/bin/node /opt/agw-demo/server.js
Restart=always
DynamicUser=yes

バックエンド VM にはパブリック IP を付けません。外向き通信 (パッケージ取得など) は NAT Gateway 経由です。受信は NSG の既定ルールで遮断するため、インターネットからバックエンドへ直接は到達できず、App Gateway 経由のみになります。

4.3 ポータルでヘッダーベースのルールを手動で作る (チュートリアルの手順)

Microsoft Learn の チュートリアル: Azure ポータルで Application Gateway の Advanced Rules を使ってヘッダーベースのルーティングを設定する の手順です。このデモは deploy.sh が作るため、通常は不要です。ポータルの操作を確かめるときに使います。

ポータルの「アプリケーション ゲートウェイの作成」では Advanced ルールを設定できません。基本ルールで作成した後に、基本ルールを Advanced に変更します。

前提: 基本ルール、リスナー、既定のバックエンド プールと設定がある Application Gateway。v2 用の 2 つ目のバックエンド プールと、そのバックエンド設定。

  1. ゲートウェイの ルール を開き、基本ルールを選ぶ。
  2. ルールの種類 を Advanced にする。
  3. リスナー タブ: ルール名 (例: rule1) と ルールの優先度 を入力する。数値が小さいほど先に評価される。リスナーは既存のものが事前に入る。
  4. ルーティング タブ: Advanced ルール名 (例: V2-app-routing) と Advanced ルールの優先度 を入力する。
  5. 条件: + Add conditions で条件セットを作る。
    • 条件セット名: V2-app-condition (条件セットの名前であり、ヘッダー名ではない)
    • 条件の種類: HTTP header / ヘッダーの種類: Custom / カスタム ヘッダー: X-App-Version / 一致の種類: Static / 値: v2
    Add Conditions を押しても、この時点ではまだ保存されない。
  6. ターゲット: + Add Targets。ターゲットの種類: Backend pool / バックエンド プール: v2 用のプール / バックエンド設定: v2 用の設定。
  7. 既定のターゲット: 基本ルールの Target と Backend Settings と同じ値になっていることを確認する (既定の振り分け先)。
  8. Review → Save。

テスト

curl http://<FRONTEND-IP>/                              # 既定のプール
curl -H "X-App-Version: v2" http://<FRONTEND-IP>/      # v2 のプール
curl -H "X-App-Version: none" http://<FRONTEND-IP>/    # 既定のプール

注意 (実際に起きた間違い)

  • 条件セット名をヘッダー名の欄に入れると、一致しない: ヘッダー名が V2-app-condition になると、X-App-Version: v2 は一致せず、既定の振り分け先に送られる。ヘッダー名は必ず X-App-Version。
  • 既存のルールを変えると、動きが変わる: partner を V2-app-routing に変えて X-App-Version: v2 の条件を AND で追加すると、X-Partner-Id だけのリクエストは pool-partner に届かなくなる。
  • ポータルでの手作業は、再デプロイで消える: deploy/main.bicep の定義で作ったルールは、deploy.sh を実行すると定義どおりに戻る。

5. シミュレーターをフロントエンドにする

5.1 現在の構成 (すぐ使える)

  1. シミュレーターでシナリオを選び [要求を送信] → 経路図・ルールごとの一致/不一致・応答 (模擬) を説明
  2. 「実機で同じ要求を送る (curl)」をコピーし、<FRONTEND-IP> を実際の IP に置き換えて実行
  3. 実機の応答ヘッダー x-backend-pool、またはブラウザーで開いたページの色・プール名が、シミュレーターの「応答」と一致することを見せる

シミュレーターのルールと deploy.sh のルールは同じ定義です。ルールを変える場合は、シミュレーターの [JSON] 表示と deploy/main.bicep の定義を見比べて両方をそろえます。Azure CLI 2.87.0 には advanced-routing のコマンドがないため、実機側はポータルの [ルール] 画面で確認します。

5.2 発展: シミュレーターから実機へ直接送信する場合の要件

単体 HTML 版 agw-routing-simulator.html は、画面上部の「ゲートウェイ URL」が空ならオフラインでシミュレーションし、URL を入れると実機に要求を送って「予測」と「実機の応答」を並べて表示します (予測と一致 / 不一致も表示)。ファイルをローカルで開けば (file://) http のゲートウェイにも送れます。ブラウザーの制約は次のとおりです。

課題原因対応
HTTPS (https のページから使う場合)https で配信されたページから http のゲートウェイへの fetch は混在コンテンツとしてブロックされる単体 HTML をローカル (file://) で開く。https のページから使う場合は HTTPS リスナーを追加
CORS別オリジンへの fetch でカスタム ヘッダー (X-Tenant-Id など) を送るとプリフライト (OPTIONS) が発生全プールの server.js で OPTIONS に応答し、Access-Control-Allow-Origin / -Allow-Headers / -Expose-Headers: x-backend-pool を返す。OPTIONS 自体も App Gateway のルーティングを通るため、全プールで同じ処理が必要
User-Agent を変えられないブラウザーの fetch では User-Agent を任意に設定できないモバイル ルールは実機のスマートフォンで開くか、デモ用にカスタム ヘッダー (例 X-Device) の条件に置き換える
Client IP は実際の IPブラウザーから送る要求の送信元は端末の実 IP実機モードでは送信元 IP はゲートウェイが見ている実際の値を使う。WAF は User-Agent (agw-block-demo) を遮断するカスタム ルールで見せる
リダイレクトを読めないfetch はリダイレクトを自動追従、redirect: "manual" では Location を読めない「リダイレクトされた」ことだけを表示する
WAF 403 の中身を読めないWAF の応答には CORS ヘッダーが付かず、fetch がネットワーク エラーになるエラー時は「ブロックされた可能性」として表示し、curl で 403 を確認
アプリからの外部通信公開アプリの実行環境が外部 URL への通信を許可するか未確認実装前に疎通テストが必要

server.js には次の CORS 対応を組み込み済みです (環境変数 ALLOW_ORIGIN、既定は *。空文字で無効化)。

const ALLOW_ORIGIN = process.env.ALLOW_ORIGIN === undefined ? "*" : process.env.ALLOW_ORIGIN;
function cors(res) {
  if (!ALLOW_ORIGIN) return;
  res.setHeader("access-control-allow-origin", ALLOW_ORIGIN);
  res.setHeader("access-control-allow-methods", "GET, HEAD, POST, PUT, DELETE, PATCH, OPTIONS");
  res.setHeader("access-control-allow-headers", "*");
  res.setHeader("access-control-expose-headers", "x-backend-pool");
  res.setHeader("access-control-max-age", "0");
}
// createServer の先頭で:
cors(res);
if (req.method === "OPTIONS" && req.headers["access-control-request-method"]) { res.writeHead(204); return res.end(); }

8. 制約・注意事項と後片付け

  • Advanced rules はプレビュー機能です。マルチサイト リスナーと L4 (TCP/TLS) プロキシでは使えません
  • 重み付け (ポート 8080 のカナリア、pool-web 90% / pool-canary 10%) は、高度なルールで WeightedDistribution を指定して作ります
  • 上限: マップ 100 / ゲートウェイ、条件セット 10,000 / ゲートウェイ、ルール 100 / マップ、条件 5 / 条件セット、値 5 / 条件、値・正規表現 128 文字
  • ARM API (2026-11-20 確認): 高度なルールでも複数プールを指定できる (backendAddressPoolsAndSettings と poolSelectionAlgorithm)。loadDistributionPolicy だけを指定すると ApplicationGatewayAdvancedRoutingRuleMustReference で拒否される。公開の REST API 仕様には複数プールの項目がない
  • WAF ポリシーはゲートウェイまたはリスナー単位で関連付け。ルール単位の WAF ポリシーは非対応
  • シミュレーターの判定はブラウザーの正規表現エンジンで近似しており、RE2 と完全には一致しません
  • deploy.sh はまだ実環境で実行していません。初回は手順ごとに結果を確認しながら実行してください
