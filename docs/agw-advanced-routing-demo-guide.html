1. 全体構成

要素役割実体
シミュレータールールの評価順・AND/OR・WAF の位置を図で説明し、同じ要求を実機に送る curl を生成するApp Builder アプリ (ブラウザー内で判定)
Application GatewayBasic リスナー → WAF → Advanced routing map → バックエンド プール / リダイレクトWAF_v2、容量 1
バックエンドどのプールが応答したか・受信ヘッダーを表示するUbuntu VM 1 台に Node.js プロセス × 6 (ポート 8080–8085)

1 台の VM で 6 プールを表現しています。各プールは同じ VM の別ポートを指し、バックエンド設定 (HTTP 設定) でポートを分けます。本番相当の構成ではプールごとに別 VM / App Service にしても手順は同じです。

2. 前提条件

  • Azure サブスクリプションと、リソース グループを作成できる権限
  • Azure CLI (az upgrade で最新化)。az network application-gateway advanced-routing-map と advanced-routing-set コマンドが使えること
  • bash 環境 (Azure Cloud Shell で可)、SSH 鍵 (--generate-ssh-keys で自動作成)
  • WAF_v2 の Application Gateway は稼働時間で課金されます。デモ後は後片付けを実施してください

3. バックエンドの作り方

3.1 設計方針

  • どのプールが応答したかが一目で分かる: プール名を大きく表示し、プールごとに色を変える。応答ヘッダー x-backend-pool にも入れて curl で判定できるようにする
  • ゲートウェイを通った証拠を見せる: 受信ヘッダーを全件表示し、App Gateway が付与する x-forwarded-for / x-forwarded-proto / x-forwarded-port / x-original-host などを強調
  • 1 ファイル・依存なし: Node.js 標準モジュールのみ。プールの違いは環境変数だけで表現
  • ヘルス プローブ用エンドポイント: /healthz が 200 を返す
  • 安全な表示: 受信値はすべて HTML エスケープして表示 (ヘッダー経由の注入を防ぐ)

3.2 エンドポイント

パス応答
/healthz200 ok (App Gateway のプローブ用)
任意のパスHTML: プール名・インスタンス・Method・Path・Query・受信ヘッダー一覧
任意のパス ?format=json または Accept: application/json同じ内容の JSON

3.4 サーバー本体 (backend/server.js) の要点

const POOL_NAME = process.env.POOL_NAME || "pool-web";
const POOL_LABEL = process.env.POOL_LABEL || POOL_NAME;
const POOL_COLOR = /^#[0-9a-fA-F]{6}$/.test(process.env.POOL_COLOR || "") ? process.env.POOL_COLOR : "#334155";
const PORT = Number(process.env.PORT || 8080);
const HOST = os.hostname();
// CORS so the standalone simulator (agw-routing-simulator.html) can call the gateway directly.
// Default "*" (demo backend, no credentials). Set ALLOW_ORIGIN="" to disable, or to one origin.
const ALLOW_ORIGIN = process.env.ALLOW_ORIGIN === undefined ? "*" : process.env.ALLOW_ORIGIN;

function cors(res) {
  if (!ALLOW_ORIGIN) return;
  res.setHeader("access-control-allow-origin", ALLOW_ORIGIN);
  res.setHeader("access-control-allow-methods", "GET, HEAD, POST, PUT, DELETE, PATCH, OPTIONS");
  res.setHeader("access-control-allow-headers", "*");
http.createServer((req, res) => {
  if (req.url === "/healthz") { res.writeHead(200); return res.end("ok"); }
  const s = snapshot(req);                       // pool, method, path, query, headers ...
  res.setHeader("x-backend-pool", POOL_NAME);    // curl / test.sh で判定に使う
  res.setHeader("cache-control", "no-store");
  // ?format=json なら JSON、それ以外は HTML ページ
}).listen(PORT);

3.5 VM への配置 (cloud-init + systemd)

deploy/make-cloud-init.sh が cloud-init.yaml を生成します。中身は次の 3 点です。

  1. Node.js をインストールし、server.js を /opt/agw-demo/ に配置 (base64 埋め込み)
  2. テンプレート ユニット agw-pool@.service を作成 (DynamicUser=yes で専用ユーザーなしに実行)
  3. プールごとに /etc/agw-demo/<pool>.env を作り、systemctl enable --now agw-pool@<pool>
[Service]
EnvironmentFile=/etc/agw-demo/%i.env
ExecStart=/usr/bin/node /opt/agw-demo/server.js
Restart=always
DynamicUser=yes

VM にはパッケージ取得のためのパブリック IP を付けますが、NSG の受信規則は作成しません (--nsg-rule NONE)。インターネットからバックエンドへ直接は到達できず、App Gateway 経由のみになります。

4. Application Gateway の構築

deploy/deploy.sh を実行すると以下を順に作成します。手順を理解できるよう、ステップごとに主要コマンドを示します。

az login
cd agw-advanced-routing-demo/deploy
./deploy.sh

4.1 ネットワークとバックエンド VM

az network vnet create -g $RG -n $VNET --address-prefixes 10.20.0.0/16 \
  --subnet-name appgw --subnet-prefixes 10.20.0.0/24
az network vnet subnet create -g $RG --vnet-name $VNET -n backend --address-prefixes 10.20.1.0/24
az vm create -g $RG -n $VM --image Ubuntu2404 --size Standard_B2s \
  --vnet-name $VNET --subnet backend --nsg-rule NONE \
  --admin-username azureuser --generate-ssh-keys --custom-data cloud-init.yaml

App Gateway 用サブネットは専用にします (他のリソースを置かない)。

4.2 WAF ポリシー

az network application-gateway waf-policy create -g $RG -n $WAF
az network application-gateway waf-policy policy-setting update -g $RG --policy-name $WAF \
  --state Enabled --mode Prevention
az network application-gateway waf-policy custom-rule create -g $RG --policy-name $WAF \
  -n BlockDemoIp --priority 10 --rule-type MatchRule --action Block
az network application-gateway waf-policy custom-rule match-condition add -g $RG --policy-name $WAF \
  -n BlockDemoIp --match-variables RemoteAddr --operator IPMatch --values "$WAF_BLOCK_CIDR"

WAF はルーティング判定より前に評価され、ブロックされた要求はルーティング エンジンに届きません。この順序をデモで見せるためのカスタム ルールです。

4.3 Application Gateway 本体

az network public-ip create -g $RG -n $GW-pip --sku Standard --allocation-method Static
az network application-gateway create -g $RG -n $GW --sku WAF_v2 --capacity 1 \
  --vnet-name $VNET --subnet appgw --public-ip-address $GW-pip --waf-policy $WAF \
  --frontend-port 80 --priority 100 \
  --servers $VM_IP --http-settings-port 8080 --http-settings-protocol Http

この時点では Basic のルール rule1 とリスナーが作られます。Advanced routing rule は Basic リスナーにのみ関連付けできます (マルチサイト リスナーは非対応)。

4.4 プローブ・バックエンド プール・バックエンド設定

4.5 リダイレクト構成 (キャンペーン ルール用)

  --type Found --target-url "https://www.contoso.com/campaign" --include-path false --include-query-string true

4.6 条件セット (Advanced routing condition set)

条件セット内の条件はすべて一致 (AND)、1 つの条件の複数値はいずれか一致 (OR) です。正規表現は RE2 互換のみです。

az network application-gateway advanced-routing-set create -g $RG --gateway-name $GW -n cs-tenant \
  --routing-conditions "[{condition-type:Header,property-name:X-Tenant-Id,property-value-matcher:{pattern:'^customer-[0-9]+\$'}},{condition-type:Path,property-value-matcher:{pattern:'^/app(/.*)?\$'}}]"
条件セット条件
cs-partnerHeader X-Partner-Id = contoso | fabrikam
cs-tenantHeader X-Tenant-Id ~ ^customer-[0-9]+$ AND Path ~ ^/app(/.*)?$
cs-apiv2Header X-Api-Version = 2 | 2.0 AND Path ~ ^/api/orders(/.*)?$
(ポート 8080)リスナー listener-canary の Basic ルール。loadDistributionPolicy で pool-web 90 / pool-canary 10 (ポート全体)
cs-campaignQueryString campaign = spring | summer
cs-mobileHeader User-Agent ~ (iPhone|Android)

4.7 Advanced routing map とルール

マップは最初のルールと同時に作成し、残りのルールを追加します。優先度は小さい順に評価され、最初に一致したルールで送信先が決まります。どれにも一致しなければ既定プール (pool-web) です。

az network application-gateway advanced-routing-map create -g $RG --gateway-name $GW -n advancedRoutingMap1 \
  --default-address-pool pool-web --default-http-settings hs-pool-web \
  --rule-name partner --priority 10 --condition-set cs-partner \
  --address-pool pool-partner --http-settings hs-pool-partner
az network application-gateway advanced-routing-map rule create -g $RG --gateway-name $GW \
  --map-name advancedRoutingMap1 -n tenant --priority 20 --condition-set cs-tenant \
  --address-pool pool-tenant --http-settings hs-pool-tenant
# api-v2 (30), mobile (60) も同様。campaign (40) は --redirect-config redirect-campaign。カナリアは 8080 の Basic ルール

4.8 リスナーのルールを Advanced に切り替える

az network application-gateway rule update -g $RG --gateway-name $GW -n rule1 \
  --rule-type AdvancedRouting --advanced-routing-map advancedRoutingMap1

CLI で切り替えられない場合はポータルで実施します: [ルール] → rule1 → [ルーティング] タブ → ルールの種類を Advanced にしてマップを選択 → [保存]。新規作成ウィザードでは Advanced ルールを設定できないため、作成後に Basic から切り替える手順になります。

5. シミュレーターをフロントエンドにする

5.1 現在の構成 (すぐ使える)

  1. シミュレーターでシナリオを選び [要求を送信] → 経路図・ルールごとの一致/不一致・応答 (模擬) を説明
  2. 「実機で同じ要求を送る (curl)」をコピーし、<FRONTEND-IP> を実際の IP に置き換えて実行
  3. 実機の応答ヘッダー x-backend-pool、またはブラウザーで開いたページの色・プール名が、シミュレーターの「応答」と一致することを見せる

シミュレーターのルールと deploy.sh のルールは同じ定義です。ルールを変える場合は、シミュレーターの [JSON] 表示と az network application-gateway advanced-routing-map show の結果を見比べて両方をそろえます。

5.2 発展: シミュレーターから実機へ直接送信する場合の要件

単体 HTML 版 agw-routing-simulator.html は、画面上部の「ゲートウェイ URL」が空ならオフラインでシミュレーションし、URL を入れると実機に要求を送って「予測」と「実機の応答」を並べて表示します (予測と一致 / 不一致も表示)。ファイルをローカルで開けば (file://) http のゲートウェイにも送れます。ブラウザーの制約は次のとおりです。

課題原因対応
HTTPS (https のページから使う場合)https で配信されたページから http のゲートウェイへの fetch は混在コンテンツとしてブロックされる単体 HTML をローカル (file://) で開く。https のページから使う場合は HTTPS リスナーを追加
CORS別オリジンへの fetch でカスタム ヘッダー (X-Tenant-Id など) を送るとプリフライト (OPTIONS) が発生全プールの server.js で OPTIONS に応答し、Access-Control-Allow-Origin / -Allow-Headers / -Expose-Headers: x-backend-pool を返す。OPTIONS 自体も App Gateway のルーティングを通るため、全プールで同じ処理が必要
User-Agent を変えられないブラウザーの fetch では User-Agent を任意に設定できないモバイル ルールは実機のスマートフォンで開くか、デモ用にカスタム ヘッダー (例 X-Device) の条件に置き換える
Client IP は実際の IPブラウザーから送る要求の送信元は端末の実 IP実機モードでは送信元 IP はゲートウェイが見ている実際の値を使う。WAF は User-Agent (agw-block-demo) を遮断するカスタム ルールで見せる
リダイレクトを読めないfetch はリダイレクトを自動追従、redirect: "manual" では Location を読めない「リダイレクトされた」ことだけを表示する
WAF 403 の中身を読めないWAF の応答には CORS ヘッダーが付かず、fetch がネットワーク エラーになるエラー時は「ブロックされた可能性」として表示し、curl で 403 を確認
アプリからの外部通信公開アプリの実行環境が外部 URL への通信を許可するか未確認実装前に疎通テストが必要

server.js には次の CORS 対応を組み込み済みです (環境変数 ALLOW_ORIGIN、既定は *。空文字で無効化)。

const ALLOW_ORIGIN = process.env.ALLOW_ORIGIN || "";   // シミュレーターのオリジン
function cors(res) {
  if (!ALLOW_ORIGIN) return;
  res.setHeader("access-control-allow-origin", ALLOW_ORIGIN);
  res.setHeader("access-control-allow-headers", "x-tenant-id, x-partner-id, x-api-version, x-device");
  res.setHeader("access-control-allow-methods", "GET, HEAD, POST, PUT, DELETE, PATCH, OPTIONS");
  res.setHeader("access-control-expose-headers", "x-backend-pool");
}
// createServer の先頭で:
cors(res);
if (req.method === "OPTIONS") { res.writeHead(204); return res.end(); }

8. 制約・注意事項と後片付け

  • Advanced rules はプレビュー機能です。マルチサイト リスナーと L4 (TCP/TLS) プロキシでは使えません
  • 上限: マップ 100 / ゲートウェイ、ルール 100 / マップ、条件 5 / 条件セット、値 5 / 条件、値・正規表現 128 文字
  • WAF ポリシーはゲートウェイまたはリスナー単位で関連付け。ルール単位の WAF ポリシーは非対応
  • シミュレーターの判定はブラウザーの正規表現エンジンで近似しており、RE2 と完全には一致しません
  • deploy.sh はまだ実環境で実行していません。初回は手順ごとに結果を確認しながら実行してください
