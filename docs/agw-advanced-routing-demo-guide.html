2. Prerequisites

  • An Azure subscription and permission to create a resource group
  • Azure CLI (signed in with az login). This guide deploys with Bicep through deploy.sh (Bicep comes with az). The advanced routing commands (az network application-gateway advanced-routing-set / advanced-routing-map) are available in Azure CLI 2.92.0 and later; section 5.1 uses them to check the gateway
  • A bash environment (Azure Cloud Shell works). deploy.sh creates an SSH key (~/.ssh/id_ed25519.pub) when there is none
  • A WAF_v2 Application Gateway is billed while it runs. Do the cleanup after the demo

3. How the backend is built

3.1 Design

  • You can see at a glance which pool answered: the page shows the pool name in large type, in a different color per pool. The name is also in the x-backend-pool response header, so curl can check it
  • It proves the request went through the gateway: the page lists every request header and highlights the ones Application Gateway adds, such as x-forwarded-for, x-forwarded-proto, x-forwarded-port, and x-original-host
  • One file, no dependencies: Node.js standard modules only. Pools differ only in environment variables
  • Health probe endpoint: /healthz returns 200
  • Safe output: every received value is HTML-escaped before it is shown (no injection through headers)

3.4 The server (backend/server.js)

An excerpt of backend/server.js: reading the environment variables, CORS, and handling a request.

const POOL_NAME = process.env.POOL_NAME || "pool-web";
const POOL_LABEL = process.env.POOL_LABEL || POOL_NAME;
const POOL_COLOR = /^#[0-9a-fA-F]{6}$/.test(process.env.POOL_COLOR || "") ? process.env.POOL_COLOR : "#334155";
const PORT = Number(process.env.PORT || 8080);
const HOST = os.hostname();
// CORS so the standalone simulator (agw-routing-simulator.html) can call the gateway directly.
// Default "*" (demo backend, no credentials). Set ALLOW_ORIGIN="" to disable, or to one origin.
const ALLOW_ORIGIN = process.env.ALLOW_ORIGIN === undefined ? "*" : process.env.ALLOW_ORIGIN;

function cors(res) {
  if (!ALLOW_ORIGIN) return;
  res.setHeader("access-control-allow-origin", ALLOW_ORIGIN);
  res.setHeader("access-control-allow-methods", "GET, HEAD, POST, PUT, DELETE, PATCH, OPTIONS");
  res.setHeader("access-control-allow-headers", "*");
  res.setHeader("access-control-expose-headers", "x-backend-pool");
  res.setHeader("access-control-max-age", "0"); // preflight is routed too; do not cache it
}
// ... (omitted: header names, page() that builds the HTML) ...
http
  .createServer((req, res) => {
    cors(res);
    if (req.method === "OPTIONS" && req.headers["access-control-request-method"]) {
      res.setHeader("x-backend-pool", POOL_NAME);
      res.writeHead(204);
      return res.end();
    }
    if (req.url === "/healthz") {
      res.writeHead(200, { "content-type": "text/plain" });
      return res.end("ok");
    }
    const s = snapshot(req);
    const wantsJson = s.query.format === "json" || /application\/json/.test(req.headers.accept || "");
    res.setHeader("x-backend-pool", POOL_NAME);
    res.setHeader("cache-control", "no-store");
    if (wantsJson) {
      res.writeHead(200, { "content-type": "application/json; charset=utf-8" });
      return res.end(JSON.stringify(s, null, 2));
    }
    res.writeHead(200, { "content-type": "text/html; charset=utf-8" });
    res.end(page(s));
  })

3.5 Putting it on the VMs (cloud-init + systemd)

deploy/make-cloud-init.sh generates one bootstrap file per VM (deploy.sh runs it). Its arguments are the input (pool definitions) and the output file.

  • cloud-init.yaml: for VM 1. The seven processes of backend/pools.conf (ports 8080–8083, 8085, 8086, 8087)
  • cloud-init-canary.yaml: for VM 2 (canary). pool-canary (port 8080), pool-fast (8086), and pool-rr-b (8087) from backend/pools-canary.conf

Both do these three things.

  1. Install Node.js 26 (the current LTS) from the NodeSource apt repository, and put server.js in /opt/agw-demo/ (embedded as base64). The repository's signing key is embedded in the file (deploy/nodesource-repo.gpg.key), not downloaded at boot. Ubuntu's own nodejs package (Node.js 18, end of life) is pinned out, so if NodeSource cannot be reached, the install fails instead of falling back to it
  2. Create the template unit agw-pool@.service (DynamicUser=yes runs it without a dedicated user)
  3. Create /etc/agw-demo/<pool>.env per pool and run systemctl enable --now agw-pool@<pool>
[Service]
EnvironmentFile=/etc/agw-demo/%i.env
ExecStart=/usr/bin/node /opt/agw-demo/server.js
Restart=always
DynamicUser=yes

The backend VMs have no public IP. Outbound traffic (package downloads and so on) goes through a NAT gateway. Inbound traffic is denied by the NSG default rules, so the internet cannot reach the backends directly; only the Application Gateway can.

4. Building the Application Gateway

Everything is in deploy/deploy.sh. You do not create resources one by one with the CLI. deploy.sh deploys the template deploy/main.bicep, which creates the resources below in one go.

This is sample output of test.sh. The Canary line is one request of the 90:10 split on port 8080, so it can be pool-web or pool-canary.

Priority-based selection (port 8090)

Port 8090 prefers pool-canary on VM 2 (Primary) and switches to pool-web on VM 1 (Standby) when the primary stops. canary-check.sh counts the x-backend-pool response header, which is the process name on the VM, so Primary shows as pool-canary and Standby as pool-web.

FRONTEND=<frontend IP>:8090 ./canary-check.sh /app/home 100   # normal
# stop pool-canary on VM 2, then wait 2–3 minutes
az vm run-command invoke -g rg-agw-advrouting-demo -n agwdemo-backend-canary --command-id RunShellScript --scripts "systemctl stop agw-pool@pool-canary"
FRONTEND=<frontend IP>:8090 ./canary-check.sh /app/home 100   # stopped
# start it again, then wait 2–3 minutes
az vm run-command invoke -g rg-agw-advrouting-demo -n agwdemo-backend-canary --command-id RunShellScript --scripts "systemctl start agw-pool@pool-canary"
FRONTEND=<frontend IP>:8090 ./canary-check.sh /app/home 100   # restored

Expected (example):

normal     all 100 requests: pool-canary (Primary = VM 2)
stopped    all 100 requests: pool-web    (Standby = VM 1)
restored   all 100 requests: pool-canary (Primary = VM 2)

The switch takes about 2–3 minutes after the stop. Right after it, pool-canary can still answer. The same process (VM 2, port 8080) is also the only server of pool-canary on port 8080 and pool-flag-on on port 8100. While it is stopped, about 10% of requests on port 8080 and requests on port 8100 with X-Feature: new also fail. Restore it as soon as the check is done. (Weighted distribution does not look at pool health, so the requests that pick pool-canary on port 8080 fail; see section 8.) The 8080 and 8100 results of test.sh can fail during the stop, so run test.sh after restoring.

Feature flag (port 8100)

On port 8100, the client turns the flag on with a header. flagMap sends requests with the header X-Feature: new to pool-flag-on (VM 2 port 8080) and everything else to the default pool-flag-off (VM 1 port 8080). x-backend-pool is the process name, so flag off shows as pool-web and flag on as pool-canary.

curl -s -D - -o /dev/null http://<frontend IP>:8100/ | grep -i x-backend-pool
curl -s -D - -o /dev/null -H "X-Feature: other" http://<frontend IP>:8100/ | grep -i x-backend-pool
curl -s -D - -o /dev/null -H "X-Feature: new" http://<frontend IP>:8100/ | grep -i x-backend-pool
no header         x-backend-pool: pool-web     (pool-flag-off, flag off)
X-Feature: other  x-backend-pool: pool-web     (pool-flag-off, flag off)
X-Feature: new    x-backend-pool: pool-canary  (pool-flag-on, flag on)

Port 80 has no feature flag rule. Always use port 8100. This is not an A/B test: the client chooses, and there is no random split (a statistical A/B test is tracked in issue #27).

Server selection (ports 8110 / 8120 / 8130)

These three ports show how the gateway picks a server inside one pool, and what happens when one server is stuck (a hot spot). 8110 is Round Robin over two fast servers. 8120 is Round Robin over pool-slow (waits 3 s) and pool-fast, so about half of the requests wait. 8130 uses Least Connections over the same two servers, so new requests avoid the slow one. x-backend-pool shows the server that answered.

FRONTEND=<frontend IP>:8110 ./lb-check.sh /app/home 100 6
FRONTEND=<frontend IP>:8120 ./lb-check.sh /app/home 100 6
FRONTEND=<frontend IP>:8130 ./lb-check.sh /app/home 100 6

Least Connections only differs from Round Robin while the slow server still holds earlier requests, so lb-check.sh and the simulator's test requests keep 6 requests open at a time (canary-check.sh sends one at a time and cannot show it). Test one port at a time: 8120 and 8130 share the same two servers. The 3 s delay is shorter than the probe timeout (20 s), so the slow server stays healthy; a server that stops answering is removed by the probe with either algorithm. Least Connections is not applied while cookie-based affinity is on, so hs-8086 keeps it off.

4.3 Creating a header-based rule by hand in the portal (the tutorial)

These are the steps of the Microsoft Learn Tutorial: Configure header-based routing with Application Gateway Advanced Rules in the Azure portal. This demo does not need them, because deploy.sh creates everything. Use them to try the portal.

The portal's "Create application gateway" experience cannot configure an Advanced rule. Create the gateway with a Basic rule, then change the Basic rule to Advanced.

Before you start: an Application Gateway with a Basic rule, a listener, and a default backend pool and settings. A second backend pool for v2 and its backend settings.

  1. Open Rules on the gateway and select the Basic rule.
  2. Set Rule type to Advanced.
  3. Listener tab: enter the rule name (for example rule1) and the Rule priority. Lower numbers are evaluated first. The existing listener is prefilled.
  4. Routing tab: enter the Advanced rule name (for example V2-app-routing) and the Advanced rule priority.
  5. Conditions: select + Add conditions and create a condition set.
    • Condition set name: V2-app-condition (the name of the condition set, not the header name)
    • Condition type: HTTP header / Header type: Custom / Custom header: X-App-Version / Match type: Static / Value: v2
    Selecting Add Conditions does not save anything yet.
  6. Targets: select + Add Targets. Target type: Backend pool / Backend pool: the v2 pool / Backend settings: the v2 settings.
  7. Default targets: check that Target and Backend Settings have the values of the Basic rule (the default destination).
  8. Review → Save.

Test

curl http://<FRONTEND-IP>/                              # default pool
curl -H "X-App-Version: v2" http://<FRONTEND-IP>/      # v2 pool
curl -H "X-App-Version: none" http://<FRONTEND-IP>/    # default pool

Mistakes that actually happened

  • Typing the condition set name into the header name field makes the rule never match: when the header name is V2-app-condition, X-App-Version: v2 does not match and the request goes to the default destination. The header name must be X-App-Version.
  • Editing an existing rule changes its behavior: renaming partner to V2-app-routing and adding the X-App-Version: v2 condition (AND) means a request with only X-Partner-Id no longer reaches pool-partner.
  • Portal edits disappear on redeploy: rules defined in deploy/main.bicep go back to their definition when deploy.sh runs.

5.2 Sending from the simulator to the real gateway (browser limits)

The standalone page agw-routing-simulator.html simulates offline while "Gateway URL" at the top is empty. With a URL, it sends the request to the real gateway and shows the prediction next to the real response (and whether they match). Opened as a local file (file://), it can also send to an http gateway. The browser sets these limits.

LimitCauseWhat to do
HTTPS (when the page is served over https)A fetch from an https page to an http gateway is blocked as mixed contentOpen the standalone HTML locally (file://). To use it from an https page, add an HTTPS listener
CORSA cross-origin fetch with custom headers (X-Tenant-Id and so on) triggers a preflight (OPTIONS)server.js answers OPTIONS in every pool and returns Access-Control-Allow-Origin / -Allow-Headers / -Expose-Headers: x-backend-pool. The OPTIONS request is routed by the gateway too, so every pool must do the same

server.js has this CORS support built in (environment variable ALLOW_ORIGIN, default *; an empty string turns it off).

const ALLOW_ORIGIN = process.env.ALLOW_ORIGIN === undefined ? "*" : process.env.ALLOW_ORIGIN;
function cors(res) {
  if (!ALLOW_ORIGIN) return;
  res.setHeader("access-control-allow-origin", ALLOW_ORIGIN);
  res.setHeader("access-control-allow-methods", "GET, HEAD, POST, PUT, DELETE, PATCH, OPTIONS");
  res.setHeader("access-control-allow-headers", "*");
  res.setHeader("access-control-expose-headers", "x-backend-pool");
  res.setHeader("access-control-max-age", "0");
}
// at the top of createServer:
cors(res);
if (req.method === "OPTIONS" && req.headers["access-control-request-method"]) { res.writeHead(204); return res.end(); }

5.3 Test requests (many requests at once)

"Send test requests" sends the selected request to its port the given number of times (100 by default), keeping 6 open at a time, and shows under "Real response" which pool or server answered each one, the average time per pool, and the total time. Use it for the ports where one request says little: the canary (8080), priority-based selection (8090), and server selection (8110 / 8120 / 8130). Each request is the one in the form (method, path, query, and headers), the same as "Send request"; headers a browser does not let a page set, such as User-Agent, are left out. Both buttons recompute the prediction from the form. Ports 8080, 8090, and 8110–8130 do not route by header, method, path, or query, and the prediction says so on those ports. Pressing the button again cancels the requests not yet sent. A request with no answer within 10 seconds counts as failed.

7. Troubleshooting

Check with deploy/test.sh and deploy/canary-check.sh. To find a cause, read the output of deploy.sh.

8. Limits and notes

  • Advanced rules are a preview feature. They cannot be used with multisite listeners or the L4 (TCP/TLS) proxy
  • Multiple pools (weighted or priority-based) work on the v2 SKUs (Standard_v2 / WAF_v2), in Basic rules, Advanced rules, and the default action of an Advanced routing map. Each place takes up to five pools and one method. This demo sets them on the :8080 and :8090 Advanced routing maps
  • Weighted distribution does not look at pool health. If the selected pool has no healthy server, the request fails. To switch pools by health, use priority-based selection
  • Limits: 100 maps per gateway, 10,000 condition sets per gateway, 100 rules per map, 5 conditions per condition set, 5 values per condition, 128 characters per value or regular expression
  • A WAF policy is associated with a gateway or a listener. A WAF policy per rule is not supported
  • The simulator approximates the rules with the browser's regular expression engine, which is not exactly RE2

9. Cleanup

After the demo, delete the whole resource group: the gateway (WAF_v2) and the backend VMs are billed while they run. deploy/cleanup.sh lists the resources, asks for the group name, and deletes the group in the background.

cd deploy
./cleanup.sh             # asks for the group name, then deletes
./cleanup.sh --dry-run   # lists the resources only
./cleanup.sh --yes       # no prompt
az group exists -n rg-agw-advrouting-demo   # false when the deletion is done
