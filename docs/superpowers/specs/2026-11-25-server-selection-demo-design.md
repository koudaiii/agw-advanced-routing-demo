# サーバー選択デモ (Round Robin / Least Connections) 設計

日付: 2026-11-25

## 目的と理由

1 台のサーバーが詰まって遅くなったとき (hot spot)、ほかのユーザーの要求が巻き込まれないようにしたい。ワークショップの参加者には、次の 2 点を実機で確かめて持ち帰ってもらう。

- Round Robin は、サーバーの状態を見ずに順番に配る。遅いサーバーがあると、要求の約半分が待たされる。
- Least Connections は、接続がたまっているサーバーを避ける。遅いサーバーがあっても、新しい要求の多くは空いているサーバーに届く。

今の実機は、どのプールもサーバーが 1 台なので、サーバー選択 (Round Robin を含む) を一つも確かめられない。シミュレーターの負荷分散欄には模擬処理があるが、「シミュレーションのみ」で実機と比べられない。

## ゴール

- 3 つのポートで、基本の動き、起きる問題、解決を順に見せる。
- 遅いサーバーは最初から遅くしておく。講師がその場で切り替える仕組みは作らない。
- 「待たされた件数」で迷惑を数え、ポートごとに比べられるようにする。
- シミュレーター、CLI のどちらからでも確かめられるようにする。

## ゴールではないもの

- Weighted Round Robin の実機デモ。別の Issue にする。
- 遅延をその場で変える仕組み。
- 既存のリスナー (80 / 8080 / 8090 / 8100) の動作の変更。

## 失敗とみなすもの

- Least Connections のポートで、Round Robin と同じ結果しか出ない。送り方や遅延の設定のせいで差が見えないなら、動いていても失敗とする。
- 遅いサーバーがヘルスプローブで異常と判定され、プールから外れる。そうなると Round Robin でも遅いサーバーを避けてしまい、比較にならない。

## 構成

```text
:8110  Round Robin (通常)        pool-rr      → VM1:8087 pool-rr-a / VM2:8087 pool-rr-b   どちらも速い
:8120  Round Robin (slow-fast)   pool-rr-slow → VM1:8086 pool-slow / VM2:8086 pool-fast   半分が 3 秒待つ
:8130  Least Connections         pool-lc      → VM1:8086 pool-slow / VM2:8086 pool-fast   遅い側を避ける
```

1 つのプールの中では全サーバーが同じポートを使うため、プロセスは 4 つになる。

| VM | ポート 8086 | ポート 8087 |
|---|---|---|
| VM 1 (192.168.1.10) | `pool-slow`: 毎回 3 秒待つ | `pool-rr-a`: 速い |
| VM 2 (192.168.1.11) | `pool-fast`: 速い | `pool-rr-b`: 速い |

- `x-backend-pool` はプロセス名を返すので、どちらのサーバーが応答したかがそのまま分かる。
- 8120 と 8130 は同じ 2 台を使う。Least Connections が接続を数える範囲 (プールごとかサーバーごとか) はドキュメントに書かれていないため、この 2 つは同時に試さない手順にする。

## 決まっていること

### バックエンド

- `backend/server.js` に遅延の設定 (環境変数 `DELAY_MS`、既定 0) を追加する。遅延は通常の要求にだけかける。`/healthz` と OPTIONS (CORS の事前確認) にはかけない。
- `backend/pools.conf` と `backend/pools-canary.conf` に、遅延の列を追加する。既存の行は 0。`deploy/make-cloud-init.sh` がこの列を `DELAY_MS` として env ファイルに書く。
- VM 1 に `pool-slow` (8086、3000 ms) と `pool-rr-a` (8087、0)、VM 2 に `pool-fast` (8086、0) と `pool-rr-b` (8087、0) を追加する。

### ゲートウェイ (`deploy/main.bicep`)

- フロントエンド ポート 8110 / 8120 / 8130、リスナー、要求ルーティング ルールを 3 組追加する。条件で振り分ける必要がないため、ルールは Basic (マップなし) にする。Microsoft Learn には、Basic のルールでもサーバー選択を使えると書かれている。公開 API 仕様で Least Connections を参照できる場所も、Basic を含む要求ルーティング ルールだけである (後述)。
- バックエンド プール `pool-rr` (2 台、8087)、`pool-rr-slow` (2 台、8086)、`pool-lc` (2 台、8086) を追加する。
- バックエンド設定 `hs-8086` と `hs-8087` を追加する。既存と同じく Cookie によるアフィニティは無効にする。Least Connections はアフィニティが有効だと使われないため。プローブは既存の `/healthz` (間隔 30 秒、タイムアウト 20 秒、異常のしきい値 3) を使う。
- `pool-lc` のサーバー選択を Least Connections にする。`pool-rr` と `pool-rr-slow` は既定の Round Robin のままにする。

### 送り方 (差を出すための条件)

Least Connections の差は、遅いサーバーに接続がたまっている間に、次の要求が届くときにだけ出る。

- 今のシミュレーターは 10 件ずつまとめて送り、10 件すべてが終わってから次の 10 件を送る。この送り方では、次の 10 件を送る時点で遅いサーバーの接続が残っていないため、Least Connections でも Round Robin とほぼ同じ半々になる。
- 1 件ずつ順に送る `deploy/canary-check.sh` も同じ理由で差が出ない。

そこで次のように変える。

- シミュレーターのテスト要求を、同時に 6 件を保ったまま、1 件終わるごとに次の 1 件を送る方式に変える。全ポートで同じ方式にする。既存のポートの集計結果は変わらない。6 件にするのは、ブラウザーが同じホストとポートへ同時に送る HTTP/1.1 の要求を約 6 件に制限するためである。これを超えると、ブラウザー内で待った時間が応答時間に混ざる。
- 1 件ごとの応答時間を記録し、結果に表示する。応答時間は、利用者が体感する時間 (ブラウザーが要求を出してから応答を受け取るまで) とする。1 秒以上かかった件数を「待たされた件数」として数える。
- CLI には、同時に送る件数 (既定 6) を指定でき、応答時間も数えるスクリプトを用意する。シミュレーターと同じ条件で比べられるようにするためである。

### 差が見えたと判断する基準

100 件、同時 6 件、遅延 3000 ms で送ったとき、次を満たせば合格とする。実機での確認を必須とする。

| ポート | 待たされた件数の目安 |
|---|---|
| 8110 | 0 件 |
| 8120 | 35〜65 件 (約半分) |
| 8130 | 10 件以下 |

8130 の目安は次の見積もりによる。遅いサーバーは接続を 3 秒持ち続けるので、空いている速いサーバーが新しい要求を受ける。遅いサーバーに次の要求が届くのは、接続が閉じた後だけである。ゲートウェイがバックエンドとの待機中の接続を「有効な接続」として数える場合は、この見積もりが外れる。その場合は実機の結果を設計書に記録し、基準を見直す。

### シミュレーター

- プリセットを 3 つ追加する。名前は英語版と日本語版の両方で用意する。
- ポートとプール名の対応、構成図のステージ、ポートの説明文に 8110 / 8120 / 8130 を追加する。
- 新しいプール名とプロセス名を、シミュレーターの既知のプールの一覧に追加する。
- 負荷分散欄 (シミュレーションのみ) の模擬処理に、サーバーごとの遅延 (接続を持ち続ける時間) と「待たされた件数」を追加する。今の模擬処理は、どのサーバーも同じ時間だけ接続を持つ前提なので、8120 と 8130 を再現すると両方とも半々になってしまう。そのうえで、8120 と 8130 に対応するプリセットを追加する。(作業する人の判断: レビューの指摘を受けて追加)

### ドキュメント

- README、構築ガイド、ワークショップのスキルを、英語版と日本語版の両方で更新する。
- 8120 と 8130 を同時に試さないこと、遅延がプローブのタイムアウトより短い理由を書く。

## 作り方の比較

| 案 | 内容 | 判断 |
|---|---|---|
| A | 1 つのポートで、ヘッダーにより Round Robin と Least Connections を切り替える | 増えるものは少ないが、ヘッダーの説明が要る。採用しない |
| B | アルゴリズムごとにポートを分ける (Round Robin の通常の例を含めて 3 つ) | 説明が単純で、基本、問題、解決の順に見せられる。**採用** |
| C | 1 つのプールのアルゴリズムを再デプロイで切り替える | 切り替えに数分かかり、並べて比べられない。採用しない |

### 既存の環境への反映

VM の設定は、最初の起動時に cloud-init で入るだけである。そのため、既存の VM には新しいプロセスが入らない。この変更は、新しく作った環境だけを対象にする。今の検証環境は `deploy/cleanup.sh` で消してから `deploy/deploy.sh` で作り直す。(作業する人の判断: 検証環境は一時的なものなので)

## ARM での Least Connections の指定 (調査結果と進め方)

2026-11-25 に調べた結果は次のとおり。

- Microsoft Learn には「サーバー選択のアルゴリズムはプールに属する」とだけ書かれている。
- 公開 API 仕様 (azure-rest-api-specs の 2026-05-01) では、Least Connections はゲートウェイ全体の `loadDistributionPolicies` に定義する。その中で対象のプールを指定し、要求ルーティング ルールか、パス ルールから `loadDistributionPolicy` で参照する。プール自体には、アルゴリズムの項目がない。
- このリポジトリで使っている高度なルールのプレビュー項目 (`backendAddressPoolsAndSettings` など) も、公開仕様に載っていない。つまり、プレビューでの正しい書き方は公開仕様だけでは確定できない。
- 検証環境のゲートウェイを 2026-07-01 で読むと、`loadDistributionPolicies` は空の配列で存在する。プールとバックエンド設定には、アルゴリズムの項目が現れない。

参照はルールごとなので、8130 のルールだけが Least Connections を参照すれば、8120 には影響しない。

進め方は次の順にする。

1. Basic のルールから、`loadDistributionPolicy` で Least Connections の設定を参照する。
2. 1 が拒否されるか、実機で差が出ない場合は、プレビューの項目 (プールの関連付けの中など) を試す。
3. どちらも使えない場合の扱いは、ユーザーと決める (未決)。

`az deployment group validate` は、知らない項目を無視することがあるため、確認には使えない。実際にデプロイし、実機で差が出るかで確かめる。

## Issue の分け方

1. バックエンドの遅延と新しいプロセス (server.js、pools.conf、cloud-init)。
2. ゲートウェイの 3 ポート (main.bicep)。1 に依存する。ARM の書き方の確認を含む。
3. テスト要求の送り方と応答時間 (シミュレーターのテスト要求、CLI スクリプト)。
4. シミュレーターの 3 ポート対応 (プリセット、名前の対応、構成図、負荷分散欄)。
5. ドキュメント (README、ガイド、スキル、英語版と日本語版)。2〜4 に依存する。
