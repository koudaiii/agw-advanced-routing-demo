# バックエンドのサーバー名とヘッダーを正す 設計書

日付: 2026-11-27

## 目的

バックエンドの各プロセスは、応答ヘッダー `x-backend-pool` で自分の名前を返している (`backend/server.js:114`、`:125`)。値は起動時の環境変数 `POOL_NAME` で、ゲートウェイは付けも書き換えもしない。つまりこのヘッダーが伝えているのは、ゲートウェイのプールではなく「応答したプロセス (サーバー)」である。

このずれが、サーバー選択のポート (:8110 / :8120 / :8130) で紛らわしさを生んでいる。

- :8120 のゲートウェイのプールは `pool-rr-slow` だが、応答には `x-backend-pool: pool-slow` と出る。`pool-slow` はプールではなく、プール内の 1 台のサーバーである。
- `pool-slow` は `pool-rr-slow` と `pool-lc` の 2 つのプールに入っている。そのため、プロセス側からはどのプールを経由したかを名乗れない。
- シミュレーターのテスト要求の結果 (集計とマス) と、応答ページの見出しには、プロセス名だけが出る。プール名はどこにも出ない。

オーナーは、実機でシミュレーターを触っている際にこの紛らわしさに気づいた (2026-11-27)。そして、変更がプロジェクト規模になっても正しい姿にそろえる、と決めた。

## 目標・非目標

- 目標: バックエンドが返すヘッダーの名前と値が、どちらも「サーバー」を指す。ヘッダーは `x-backend-srv`、値は `srv-` で始まるサーバー名にする。
- 目標: シミュレーターで実機の応答を見せるすべての場所に、「ゲートウェイのプール › サーバー」の両方を出す (例: `pool-rr-slow › srv-slow`)。
- 目標: シミュレーター、確認用のスクリプト、日英のガイド、README、ワークショップのスキルが、新しい名前と一致する。
- 非目標: ゲートウェイの構成は変えない。プール名 (`pool-web` など 13 個)、ルール、条件、重み、優先度、最小正常割合、サーバー選択の方式、ポートは今のままにする。
- 命名の原則: **プール名は、Azure Portal で見えるゲートウェイの実際のバックエンド プール名を使う。サーバー名は、それとは別に `srv-` で始まる名前を付ける。** たとえば :8080 では、プールは `pool-web`、サーバーは `srv-web` である。こうすると、シミュレーターやガイドに出るルールとプールの名前は、すべて Azure Portal の Application Gateway のルールとバックエンド プールにそのままひも付く。(オーナーの指示、2026-11-27)
- 非目標: シミュレーターの使い方のヒントと画面の整理は、この変更の後に別の設計書で扱う。表示を変える場所が重なるので、名前を先に確定させる。
- 反目標: 表示やヘッダーの名前が、実際の設定と食い違うこと。プールの名前とサーバーの名前がはっきり分かれていて、どちらも実際の設定と一致していれば、読み手は混乱しない。(オーナーの判断、2026-11-27。ヘッダーの数そのものは問題ではない)
- 制約: `x-backend-srv` の値には、必ずサーバー名 (`srv-` で始まる名前) を入れる。(オーナーの指示、2026-11-27)

## 検討した方式

| 方式 | 内容 | 判断 |
|---|---|---|
| A. 表示だけを直す | 名前とヘッダーは今のまま。シミュレーターがポートからプール名を補い、「pool-rr-slow › pool-slow」と出す | 変更は小さいが、curl やガイドで `x-backend-pool: pool-slow` を見たときの紛らわしさが残る。不採用 |
| B1. ヘッダーを使い分ける | 全プロセスが `x-backend-srv` を返し、プールが 1 つに決まる 10 個は `x-backend-pool` も返す | 不採用。ヘッダーが 2 種類あること自体は問題ではない (反目標の項)。ただ、プール名はゲートウェイが決めるもので、バックエンドには分からない。`srv-slow` / `srv-fast` は 2 つのプールに入っているので、`x-backend-pool` を正しく返せない。プール名は、シミュレーターが Azure の実際のプール名で補う |
| B2. ヘッダーを `x-backend-srv` の 1 種類にし、サーバー名を変える | 4 個 (サーバー選択用) だけ `srv-` に変える | 残り 10 個が `x-backend-srv: pool-web` になり、サーバーのヘッダーにプール名が入る (制約と反目標に反する)。不採用 |
| **B3. ヘッダーを `x-backend-srv` の 1 種類にし、14 個すべてを `srv-` に変える** | 名前とヘッダーの両方がサーバーを指す。プール名はシミュレーターが補う | **採用** (オーナーが選択、2026-11-27) |

## 構成

### サーバー名 (backend/pools.conf、backend/pools-canary.conf)

ポート、ラベル、色、遅延は変えない。変えるのは名前だけである。

| 今の名前 | 新しい名前 | VM | ポート | 所属するゲートウェイのプール |
|---|---|---|---|---|
| `pool-web` | `srv-web` | VM 1 | 8080 | `pool-web` |
| `pool-partner` | `srv-partner` | VM 1 | 8081 | `pool-partner` |
| `pool-tenant` | `srv-tenant` | VM 1 | 8082 | `pool-tenant` |
| `pool-api-v2` | `srv-api-v2` | VM 1 | 8083 | `pool-api-v2` |
| `pool-mobile` | `srv-mobile` | VM 1 | 8085 | `pool-mobile` |
| `pool-slow` | `srv-slow` | VM 1 | 8086 | `pool-rr-slow`、`pool-lc` |
| `pool-rr-a` | `srv-rr-a` | VM 1 | 8087 | `pool-rr` |
| `pool-standby` | `srv-standby` | VM 1 | 8088 | `pool-standby` |
| `pool-flag-off` | `srv-flag-off` | VM 1 | 8089 | `pool-flag-off` |
| `pool-canary` | `srv-canary` | VM 2 | 8080 | `pool-canary` |
| `pool-fast` | `srv-fast` | VM 2 | 8086 | `pool-rr-slow`、`pool-lc` |
| `pool-rr-b` | `srv-rr-b` | VM 2 | 8087 | `pool-rr` |
| `pool-primary` | `srv-primary` | VM 2 | 8088 | `pool-primary` |
| `pool-flag-on` | `srv-flag-on` | VM 2 | 8089 | `pool-flag-on` |

`srv-` という接頭辞は、シミュレーターの負荷分散欄ですでにサーバーを `srv-1`、`srv-2` と呼んでいることとも揃う。

### バックエンド (backend/server.js)

- 応答ヘッダーを `x-backend-pool` から `x-backend-srv` に替える。通常の応答と、CORS のプリフライト (204) の両方が対象である。
- `access-control-expose-headers` を `x-backend-srv` にする。これを忘れると、curl では見えるのに、ブラウザーのシミュレーターでは「ヘッダーなし」になる。
- 環境変数を `POOL_NAME` / `POOL_LABEL` / `POOL_COLOR` から `SERVER_NAME` / `SERVER_LABEL` / `SERVER_COLOR` に替える。(作業者の判断: 「1 プロセス = 1 サーバー」とそろえるため。旧名の読み替えは残さない。)
- JSON の応答のキーを `pool` / `poolLabel` から `server` / `serverLabel` に替える。(作業者の判断: 同上)
- HTML ページの見出し「Backend pool that answered this request」を、サーバーを指す文言に替える。`<title>` も同じ。
- 先頭のコメント「One process = one backend pool.」を「1 プロセス = 1 サーバー」の意味に直す。

### VM の初期化 (deploy/make-cloud-init.sh、cloud-init 2 本)

- systemd のユニットを `agw-pool@.service` から `agw-srv@.service` に替える。(作業者の判断: ユニット名にも pool が残らないようにする。) `.env` に書く変数名も上に合わせる。
- `cloud-init.yaml` と `cloud-init-canary.yaml` は `make-cloud-init.sh` で作り直す。手で編集しない。
- 優先度ベースの停止手順は `systemctl stop agw-srv@srv-primary` / `systemctl start agw-srv@srv-primary` になる。

### ゲートウェイ (deploy/main.bicep)

- リソースは変えない。`pools` の一覧の `name` はゲートウェイのプール名なので、そのまま残す。
- 「same as backend/pools.conf」のように、プロセス名とプール名が同じだと読めるコメントを直す。どのサーバーがどのプールに入るかの対応を、コメントで示す。
- VM 2 の見出しのコメントにある `pool-canary 8080, pool-fast 8086, …` を、サーバー名に直す。

### 確認用のスクリプト (deploy/test.sh、canary-check.sh、lb-check.sh)

- `x-backend-pool` を読む箇所を `x-backend-srv` にする。
- 集計の出力は、サーバー名で数える。期待値の説明 (例: 「about 90 pool-web / 10 pool-canary」「few on pool-slow」) をサーバー名に直す。スクリプトはプール名を補わない。(作業者の判断: スクリプトはヘッダーの事実だけを出し、プールとの対応は説明文で示す。)

### シミュレーター (agw-routing-simulator.html)

- 実機の応答から `x-backend-srv` を読む。`x-backend-pool` には頼らない。旧ヘッダーへの後方互換も入れない (下の「実機」を参照)。
- サーバー名からゲートウェイのプールを求める表を 1 か所に持つ。
  - :80 / :8080 / :8090 / :8100: `srv-X` → `pool-X` (1 対 1)。
  - :8110 / :8120 / :8130: ポートで決まる (`SERVER_SELECT_PORTS`)。`srv-slow` はポートによって `pool-rr-slow` か `pool-lc` になる。
- 実機の応答を見せる次のすべての場所で、「プール › サーバー」の両方を出す。
  - 経路の文 (`describe`)
  - 予測と実機の候補一覧 (`serverSelectBlock`、`poolSelectBlock`)
  - 応答ページの見出し (`backendPage`)
  - ヘッダーがない応答などの状態表示 (`statusBlock` の `x-backend-…` の行)
  - 送信履歴の 1 行 (`HTTP 200 / …`)
  - テスト要求の結果の集計 (凡例) と、各マスの title。マスは幅 70px なので本文はサーバー名だけでもよい。プール名は title と凡例で必ず示す。(作業者の判断)
- 予測と実機の一致判定 (今の `l.pool === d.pool`、`agw-routing-simulator.html:701` 付近) は、サーバー名をプールに変換してから比べる。
- 経路図の右側を「④ マップ / ルール → ⑤ プール → ⑥ サーバー」の 3 列にする (オーナーが選択、2026-11-27)。詳しくは下の「経路図 (3 列)」。
- `SERVER_INFO`、`PRIORITY_COLOR` をサーバー名にする。色は今のものを引き継ぐ。
- オフライン (予測のみ) の表示も同じ形にそろえる。予測の代わりに描くバックエンドのページ (`renderSim` の `backendPage`) は、実機の新しいページ (見出し、`x-backend-srv`) と同じ見た目にする。1 対 1 のプールではサーバーが決まるので「`pool-tenant › srv-tenant`」と出す。サーバー選択のポートでは、今と同じく 2 台を候補として並べる。(作業者の判断: 予測と実機で見た目が違うと、比べにくくなるため。`serverSelectBlock` / `poolSelectBlock` はモードで分けない。)
- 「実機へのテスト要求」の停止手順を `agw-srv@srv-primary` にする (英日)。
- 負荷分散欄 (シミュレーションのみ) のプリセットで使っている `pool-slow` / `pool-fast` などのサーバー名も `srv-` にそろえる。ゲートウェイのプール名 (`pool-rr-slow` など) は変えない。

### 経路図 (3 列)

今の経路図は、マップ / ルールの箱から VM の枠の行へ直接線を引いている。行にはプール名とサーバー名が混在しており (`pool-web` と `pool-slow` が同じ形の行に並ぶ)、:8120 のプール `pool-rr-slow` は左の箱の小さな文字にしか出ない。

これを、オーナーが貼った階層 (④ Advanced routing map → ⑤ プール選択 → ⑥ サーバー選択) と同じ 3 列にする。

```
 ④ マップ / ルール       ⑤ プール               ⑥ サーバー

┌───────────────────┐   ┌──────────────┐      │ ┌──────────────────────┐ │
│ rule-priority     │───│ pool-primary │──────│─│ srv-primary   :8088  │ │
└───────────────────┘   └──────────────┘      │ └──────────────────────┘ │
         ...                   ...            │          ...             │
┌───────────────────┐   ┏━━━━━━━━━━━━━━┓      │ ┏━━━━━━━━━━━━━━━━━━━━━━┓ │

└───────────────────┘   └──────────────┘ │ ┃  │          ...             │
```

- **④ マップ / ルール列:** 今の 7 個の箱を使う。命名の原則に合わせ、箱の名前を Azure Portal のルール名とマップ名にする。1 行目がルール名、2 行目がマップ名 (Advanced) か「Basic」である。
  | ポート | リスナー | ルール | マップ |
  |---|---|---|---|
  | 80 | `listener-http` | `rule1` | `advancedRoutingMap1` |
  | 8080 | `listener-canary` | `rule-canary` | `canaryMap` |
  | 8090 | `listener-priority` | `rule-priority` | `priorityMap` |
  | 8100 | `listener-flag` | `rule-flag` | `flagMap` |
  | 8110 | `listener-rr` | `rule-rr` | (Basic) |
  | 8120 | `listener-rr-slow` | `rule-rr-slow` | (Basic) |
  | 8130 | `listener-lc` | `rule-lc` | (Basic) |
- **リスナー:** 列は増やさない。今の「Basic リスナー」の箱 1 つのまま、要求が通ったリスナーの Portal の名前とポートを出す (例: `listener-rr-slow :8120`)。リスナー、ルール、マップはこのデモでは 1 対 1 対 1 で、分岐がない。列にしても、線は 7 本の平行線になり、情報は増えないまま図が広がる。さらに WAF は 1 つの箱なので、7 個のリスナーから WAF へ線が集まり、図が込み入る。(作業者の判断。オーナーの問い「リスナーも分けるべきか」への回答、2026-11-27)
- **⑤ プール列:** ゲートウェイの 13 個のプールを 1 つずつ箱にする (`pool-web`、`pool-partner`、`pool-tenant`、`pool-api-v2`、`pool-mobile`、`pool-canary`、`pool-primary`、`pool-standby`、`pool-flag-on`、`pool-flag-off`、`pool-rr`、`pool-rr-slow`、`pool-lc`)。:80 の既定プールには今と同じく「(既定)」を付ける。
- **⑥ サーバー列:** VM 2 と VM 1 の大きな枠の中に、14 個のサーバーを 1 つずつ箱にして入れる。箱には、サーバー名、ポート、ラベル (例: 「3 s」) を書く。
- **線:** 「マップ / ルール → プール」は、:80 のルールの行き先、:8080 の重み、:8090 の優先度、:8100 のフラグを表す。「プール → サーバー」は、プールの中身を表す。`pool-rr-slow` と `pool-lc` の両方から `srv-slow` と `srv-fast` に線が出るので、2 つのプールが同じ 2 台を共有していることが図から読める。
- **リダイレクト:** サーバー列と同じ位置で、VM の枠の外 (下) に箱を置く。`rule1` (`advancedRoutingMap1`) から、プール列を通らずに直接点線で結ぶ。リダイレクトは `advancedRoutingMap1` の規則 `campaign` が `redirectConfiguration` で定義しており (`deploy/main.bicep:816-826`)、302 はゲートウェイ自身が返すため、プールにもサーバーにも届かない。(オーナーの提案、2026-11-27)
- **強調:** 通った経路の箱と線を、今と同じく色付きの太線にする。予測が 1 つのサーバーに決まらない場合 (:8080 の重み付け、:8110〜:8130 のサーバー選択) は、今と同じく候補をすべて強調する。予測はプール単位なので、1 対 1 のプールではプールとサーバーの両方を、サーバー選択ではプールと 2 台の候補を強調する。
- **図の幅:** 1 列増えるため、今の 1034 から広げる (1300 前後の見込み)。図はすでに `scroll-x` の中にあるので、スマートフォンでは横スクロールが増える。オーナーは了承済み (2026-11-27)。
- **線の交差:** サーバーは VM ごとにまとまり、プールは役割ごとに並ぶので、線が交差しやすい。プールの並び順は、交差が少なくなるように作業者が決める。
- 今の実装では、マップの行き先をプール名で引いている (`mapTargets`、`hitSet`)。3 列にすると「マップ → プール」と「プール → サーバー」の 2 段の対応になる。後者は、上の「サーバー名からゲートウェイのプールを求める表」と同じものを使う。

## 実機

- VM の初期化データ (customData) が変わるため、今の環境は作り直す (`./cleanup.sh` → `./deploy.sh`)。前回 (2026-11-26) と同じ手順である。
- 作り直すと、ゲートウェイの公開 IP (今は 20.222.123.60) が変わる可能性が高い。
- **作り直しはマージの前に行う** (オーナーが選択、2026-11-27)。ブランチのコードで環境を作り直し、上の「確かめ方」の実機の確認をすべて済ませてから、マージする。実機の確認はマージの条件である。
- `./cleanup.sh` は環境を消すので、実行の直前にオーナーへ一声かける。
- シミュレーターは旧ヘッダーを読まないが、この順番なら、マージ後に旧環境と食い違う期間はない。

## 作業の分け方 (提案)

1 つの Issue で、PR を 1 つにする。サーバー名とヘッダー (バックエンド)、それを読むシミュレーターとスクリプト、それを説明する文書を別々にマージすると、その間だけ食い違うためである。
