# 優先度ベースと機能フラグの専用プロセス 設計書

日付: 2026-11-26

## 目的

:8090 (優先度ベース) と :8100 (機能フラグ) のゲートウェイ プールは、どちらも :8080 のプロセスを流用している。

| ゲートウェイのプール | 指しているプロセス |
|---|---|
| `pool-primary` (:8090 優先度 1) | VM 2 の `pool-canary` (:8080) |
| `pool-standby` (:8090 優先度 2) | VM 1 の `pool-web` (:8080) |
| `pool-flag-on` (:8100 オン) | VM 2 の `pool-canary` (:8080) |
| `pool-flag-off` (:8100 オフ) | VM 1 の `pool-web` (:8080) |

この流用から、紛らわしい挙動が 2 つ生まれている。

- **停止の影響が広がる:** :8090 の切り替えを見せるために `pool-canary` を止めると、:8080 の約 10% と、:8100 の `X-Feature: new` の要求も失敗する (#119 で注記を足した)。
- **応答の名前が合わない:** `x-backend-pool` にはプロセス名が出るため、:8090 と :8100 の応答に `pool-canary` / `pool-web` と表示される。シミュレーターは、`PRIORITY_NAME_ON_8090` と `FLAG_NAME_ON_8100` でゲートウェイのプール名に読み替えている。

役割ごとに専用のプロセスを動かし、どちらもなくす。

## 目標・非目標

- 目標: :8090 の確認で止めるプロセスが、:8090 以外のポートに影響しない。
- 目標: :8090 と :8100 の応答の `x-backend-pool` が、ゲートウェイのプール名と一致する。
- 目標: シミュレーター、日英のガイド、README、ワークショップのスキルが、新しい構成と一致する。
- 非目標: ゲートウェイのルール、条件、重み、優先度、最小正常割合 (60%) は変えない。:8080 のカナリアと :8110〜:8130 のサーバー選択も変えない。
- 反目標: VM を増やすこと。費用とデプロイ時間が増える。

## 検討した方式

| 方式 | 内容 | 判断 |
|---|---|---|
| A. 新しいポートで専用プロセスを動かす | 役割ごとに、両方の VM で新しいポートのプロセスを動かす | **採用** |
| B. :8080 のままプロセスを分ける | 1 台の VM で同じポートを 2 つのプロセスが使うことになる | 不可能 |
| C. 役割ごとに VM を増やす | 分離はできるが、VM が 2 台以上増える | 反目標に当たるため不採用 |

範囲について、オーナーは「優先度だけ」ではなく「優先度と機能フラグの両方」を選んだ (2026-11-26)。機能フラグは止める手順がないので壊れはしないが、表示の紛らわしさは優先度と同じだからである。

## 構成

### プロセス (backend/pools.conf、backend/pools-canary.conf)

| プロセス (= ゲートウェイのプール) | VM | ポート | 役割 |
|---|---|---|---|
| `pool-primary` | VM 2 (192.168.1.11) | 8088 | :8090 優先度 1 |
| `pool-standby` | VM 1 (192.168.1.10) | 8088 | :8090 優先度 2 |
| `pool-flag-on` | VM 2 (192.168.1.11) | 8089 | :8100 機能フラグ オン |
| `pool-flag-off` | VM 1 (192.168.1.10) | 8089 | :8100 機能フラグ オフ (既定) |

- 8088 と 8089 は、既存のプロセスでもゲートウェイのリスナーでも使っていない。
- 遅延は 0。色はシミュレーターの既存の色に合わせる (`pool-primary` #b45309、`pool-standby` #475569、`pool-flag-off` #0369a1、`pool-flag-on` #be185d)。
- プロセス数は、VM 1 が 7 から 9 に、VM 2 が 3 から 5 に増える。

### ゲートウェイ (deploy/main.bicep)

- 4 つのプールの宛先を、新しいプロセス (8088 / 8089) にする。プールのアドレスは今と同じ VM の IP で、ポートはバックエンド設定で決まる。
- :8090 と :8100 のバックエンド設定を、`hs-pool-web` (8080) から 8088 / 8089 の設定に替える。`priorityMap` (規則 `priority-split` の 2 つのプールと既定) と `flagMap` (規則 `flag-on` と既定) が対象である。
- 新しいバックエンド設定は、既存と同じく `cookieBasedAffinity: 'Disabled'`、`requestTimeout: 20`、プローブ `healthz` を使う。
- 実装の形 (`pools` の一覧に VM の欄を足して自動で作るか、`hs-8086` / `hs-8087` と同じくポートで作るか) は、実装者が決める。

### 変更後の挙動

- :8090: 正常時は 100 件すべて `pool-primary`。`agw-pool@pool-primary` (VM 2) を止めて 2〜3 分後は `pool-standby`。:8080 と :8100 は影響を受けない。
- :8100: `X-Feature: new` は `pool-flag-on`、それ以外は `pool-flag-off`。`x-backend-pool` にもその名前が出る。
- 停止の手順は `systemctl stop agw-pool@pool-primary` / `systemctl start agw-pool@pool-primary` になる。

### シミュレーター

- `POOLS` の `pool-flag-off` / `pool-flag-on` のポートを 8089 にし、経路図の `pool-primary` / `pool-standby` の行を「:8088 優先度 1 / 2」にする。
- `PRIORITY_NAME_ON_8090` と `FLAG_NAME_ON_8100` による読み替えをなくす。応答のプロセス名を、そのままプール名として数える。
- 「実機へのテスト要求」の停止手順を `agw-pool@pool-primary` にする。「停止中は 8080 と 8100 も失敗する」という注記は、「止まるのは :8090 の Primary だけ」という内容に替える。

### ガイドの図 1

図 1 の SVG は、前回 (#109) と同じくスクリプトで英日を生成し、すべての文字が箱に収まることを確かめる。VM の枠に 8088 / 8089 の行が増えるため、図は縦に伸びる。

## 確かめ方

- シミュレーターの変更は TDD で行う。先にテストを変えて失敗を見る。
  - :8090 / :8100 で、応答の `x-backend-pool` が `pool-primary` / `pool-flag-on` などのときに、その名前で数える (代役ゲートウェイを使う)。
  - 停止手順の注記に `agw-pool@pool-primary` が出て、8080 と 8100 の失敗は書かれていない (英日)。
  - 経路図の行に `:8088` と `:8089` が出る。
- `backend/server.test.js` と `tests/simulator.test.mjs` の全体が通る。
- `az deployment group validate` か実機へのデプロイで、テンプレートが通る。
- 実機で次を確かめる: `test.sh` の機能フラグが `pool-flag-off` / `pool-flag-on` を返す。:8090 が `pool-primary` を返す。`pool-primary` を止めると、:8090 は `pool-standby` になり、:8080 と :8100 は失敗しない。
